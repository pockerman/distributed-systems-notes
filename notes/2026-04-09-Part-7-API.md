# Lesson 10: APIs

## Overview

We have seen how to establish reliable and secure connections between distributed processes. We also saw how to discover the IP address of a server using the
Domain Name System (DNS). In this lesson we discuss how a service is exposed to the outside world, or to the rest of a distributed system.
Typically, a service exposes an API (application programming interface) that external actors use to interact with it. There are different API styles. The most
common are:

- [REST](https://www.ibm.com/think/topics/rest-apis)
- [GraphQL](https://graphql.org/)
- [gRPC](https://grpc.io/)

We briefly review these in this lesson.

## APIs

Perhaps the most common API style at the time of writing is REST, so let's start with it.

### RESTful APIs

A RESTful API is an API that conforms to the design principles of the representational state transfer (REST) architectural style.
REST was defined in 2000 by computer scientist Roy Fielding in his doctoral dissertation [2]. It gives developers a relatively high level of flexibility, consistency, scalability, and efficiency. REST APIs are a lightweight way to build web APIs, and they are commonly used to exchange data between applications, web services, and databases, and to connect the components of microservices architectures. A RESTful API is typically implemented on top of the [HTTP](2026-04-09-Part-8-HTTP.md) protocol. The REST style suits systems that
are resource-centred: each resource is identified by a URL, and clients manipulate resources through the standard HTTP methods such as `GET` and `POST`. A REST API can be implemented in any programming language.

::: {.callout-note title="Remark"}
REST is not tied to HTTP; however, most web services use HTTP as their underlying protocol.
Similarly, REST can work with any data format, although JSON is the most commonly used.
:::

A RESTful API should conform to the following constraints [2]:

- Uniform interface
- Client/server decoupling
- Statelessness
- Cacheability
- Layered system architecture
- Code on demand (optional)

We won't go over the details of these here; see also [Some Best Practices in API Design](https://github.com/pockerman/qubit-notes/blob/main/software_engineering/2025-08-16-some-best-practices-api-design.md).

### GraphQL

Applications often make several requests to render a single view. For example, to display a single pull request, GitHub's REST API required four separate calls:
one for the pull request itself, one for its commits, one for its comments, and one for its reviews [5]. Each request added latency and consumed bandwidth, since
each response also contained fields the view did not need. GraphQL is a solution to this problem of needing many API calls (and over-fetching data) to serve one view.

GraphQL was developed at Facebook to load data that would otherwise require several requests to different endpoints.
GraphQL exposes data through a single endpoint, in contrast to a REST API, which exposes data through many endpoints. The data is described by a strongly typed schema, which lets clients and servers read and write data in a structured, self-documenting way.
GraphQL is particularly useful in two scenarios:

- When a client needs to gather data from multiple sources.
- When several client applications share one data source but need different views of the data. With GraphQL, each application asks for exactly the fields it presents to the user instead of receiving all of them.

GraphQL takes a fundamentally different approach from REST [5]: the client sends a query describing the shape of the response it needs, rather than the server deciding what data each endpoint returns [5]. A mobile client displaying a user profile can request the user's name, avatar, and last five posts in a single query, and receive precisely that data, with no wasted bytes.

GraphQL has trade-offs, though. Arbitrary client queries can be expensive to execute, so servers need query cost limits; HTTP caching is harder because everything goes through one endpoint; and for simple server-to-server communication its flexibility is rarely needed. It can also be more CPU-intensive to run on the server than a REST API.

### gRPC

The final API style we consider is gRPC. As we saw above, GraphQL optimizes the flexibility of client requests.
gRPC, on the other hand, optimizes the efficiency of the data transmission itself [5]. gRPC was developed by Google and is used by companies such as Netflix, Uber, Spotify, and Dropbox [5].

gRPC combines [protocol buffers](https://protobuf.dev/) for binary serialization with HTTP/2 for transport. The result is much smaller messages and faster parsing than JSON-based protocols, and gRPC inherits HTTP/2's features, such as multiplexing many calls over one connection and streaming in both directions. This makes it a good fit for high-throughput backends and for devices with limited CPU and memory. gRPC is a strong choice when designing a low-latency, highly scalable distributed system, especially a backend made of many interconnected microservices. It also offers built-in features such as deadline propagation, cancellation, retries, and request hedging.

gRPC has some downsides, too. Browsers cannot speak native gRPC, so web clients need a proxy such as gRPC-Web. Binary messages are harder to inspect and debug than JSON. And although gRPC officially supports many languages, if your language, or a consumer's language, is not on the list, you will have to look for workarounds or choose another option.

See [gRPC Hands On](appendix/2026-05-05-API-Basics-gRPC-101.md) in the appendix for a simple example of how to use gRPC, with a Python server streaming responses to a Go client.

## Summary

::: {.callout-note title="Summary"}
Services in distributed systems expose their functionality through APIs. This lesson focused on three common styles: REST, GraphQL, and gRPC. RESTful APIs, based on Roy Fielding's REST principles, are the most widely used; they model resources and rely on HTTP methods like `GET` and `POST`, while adhering to constraints such as statelessness and a uniform interface. GraphQL, developed at Facebook, lets clients query exactly the data they need from a single endpoint using a typed schema, which makes it ideal for aggregating data from multiple sources or serving diverse clients, though it complicates caching and can be more resource-intensive. gRPC, built on protocol buffers and HTTP/2, emphasizes performance and efficiency, making it well suited for low-latency microservice backends, but it needs a proxy for browsers and its binary messages are harder to debug.
:::
