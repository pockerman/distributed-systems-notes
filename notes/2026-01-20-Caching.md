# Lesson 16: Caching Methods

## Overview

We have discussed [data partitioning](2025-08-04-partitioning.md) and [data replication](2025-04-22-data-replication.md)
as means of improving system availability and reducing latency. In this lesson we discuss yet another technique: caching.
Caching is a form of data replication that offers best-effort guarantees [2].
Specifically, in this lesson we briefly discuss the following approaches to caching:

- Cache-aside caching
- Read-through caching
- Write-through caching
- Write-behind caching
- Client-side caching
- Distributed caching

## Caching methods

Let's first see what caching is. Caching is a technique whereby we keep a temporary copy
of the data closer to where the data is accessed. (We can also cache the _absence_ of data; see [Lesson 19: Negative Caching](2026-04-28-Negative-Caching.md).)
Thus, apart from the main storage, we maintain one or more copies of the data in one or more locations [1]. In web applications,
we typically don't cache the whole dataset but rather a small, frequently accessed portion of it. Caching unavoidably brings up the
issue of data consistency, i.e. how up to date the cached data is. We discuss one way to deal with this, time-to-live, in [Lesson 18: Cache Replacement](2026-01-26-Cache-Replacement.md).

::: {.callout-note title="Caching is difficult"}
The main challenge with caching is cache invalidation, i.e. making sure cached data is updated when the underlying data changes.
Phil Karlton famously called it one of the two hard things in computer science [3].
For example, Meta's engineering team spent years improving the cache consistency of their TAO system from six nines to ten nines, i.e. from 99.9999% to 99.99999999% [3].

The difficulty arises from the nature of modern systems: the cache is mutated both when it is filled on reads and when invalidations are processed on writes.
When a cache fill and an invalidation for the same key are in flight at the same time, they can arrive out of order and leave stale data in the cache indefinitely [3].
:::

Now that we understand what caching is, let's look at some approaches to it.
For more information on these approaches see [1].

### Cache-aside caching

This is probably the most commonly used caching strategy [1]. In this approach we maintain a cache,
either as a separate server, e.g. Redis, or inside the application. When the item we are looking
for is in the cache, i.e. a cache hit, access latency is very small. When the item is not found, the cache
reports a miss and the application queries the database. The application is also responsible for populating
the cache with the result.

### Read-through caching

This is similar to cache-aside. The difference is that in read-through caching the cache itself is responsible for querying
the database on a miss and updating itself. The cache is therefore not a passive component.

### Write-through and write-behind caching

The two approaches above are strategies for caching reads [1]. Often we also want the cache to handle writes.
With cache-aside, the application is responsible for writes, as the cache is a passive component.
With read-through caching, however, we have two options [1]:

- Write-through caching
- Write-behind caching

In write-through caching, an update to the cache is propagated immediately, i.e. synchronously, to the backing store [1].
The write completes only once the backing store has acknowledged it, so the write latency is dominated by the latency of the backing store, which can be significant [1].

In write-behind (or write-back) caching, the write completes as soon as the cache is updated, and the update is propagated to the backing store asynchronously.
The cache may therefore accept multiple updates before writing them to the database [1]. Writes are fast, but updates can be lost if the cache fails before flushing them.

### Client-side caching

Cache servers like Redis keep data in memory. However, the application must still talk to the server
over the network using the Redis protocol. Depending on the application, this may not be good enough,
as this last-mile latency can still be significant [1].

Client-side caching places the cache layer inside the application itself [1].
It typically combines read-through and write-behind caching, so that both reads and writes are fast [1].
Note, however, that client-side caching makes transactions hard to guarantee, because of the additional indirection and latency between the application and the database [1].

### Distributed caching

Finally, let's discuss distributed caching. Often the cache itself needs to be distributed: we use multiple cache nodes to reduce geographic latency and to handle higher workloads. In this setup, the cached data is typically partitioned across nodes, to avoid storing everything everywhere, and replicated, to improve availability and reduce access latency. Distributed caching therefore combines the advantages, and also the complexities, of caching, partitioning, and replication, and requires careful design to manage these trade-offs.

## Summary

::: {.callout-note title="Summary"}
Caching is a core technique for improving performance and reducing latency by keeping temporary copies of frequently accessed data close to where it is used. Unlike full replication, caching typically stores only a subset of the data, and it raises important consistency concerns, with cache invalidation being notoriously hard.

Common caching strategies are:

- Cache-aside: the application manages the cache, reading from it first and populating it on misses.
- Read-through: the cache itself fetches missing data from the database.
- Write-through: writes update the cache and the database synchronously, keeping them consistent but increasing write latency.
- Write-behind: writes update the cache immediately and propagate to the database asynchronously, improving performance at the cost of temporary inconsistency and possible data loss.
- Client-side caching: the cache lives inside the application, minimizing network latency but complicating transactions and consistency.
- Distributed caching: cache data is partitioned and replicated across multiple nodes to improve scalability, availability, and geographic latency, inheriting the complexities of both partitioning and replication.
:::
