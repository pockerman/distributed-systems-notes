# Introduction to Distributed Systems

## Overview

In this series of notes we discuss how to design distributed software systems.
Specifically, we discuss the fundamental challenges that have to be addressed in order to build and operate
distributed systems. We will place more emphasis on systems.

## Introduction

Before embarking on the journey of distributed system design, let's first try to answer the question: what is a distributed system?
There are plenty of definitions available. Below is a famous one attributed to Leslie Lamport [1]:

> A distributed system is one in which the failure of a computer you didn't even know existed can render your own computer unusable.

Another definition is, see [2]:

> A distributed system is a collection of collaborating, concurrent components that communicate with one another by sending and receiving messages over a network.

Perhaps the most widely known distributed system is the internet. A web application is another example of a distributed system, or can become one, depending
on its needs. Since this is a very common example, we will use it as the driving example in these notes.

A distributed system has five pillars:

- Performance
- Resilience
- Availability
- Scalability
- Security

Let's see what these terms imply and we will delve in  later sections more into techniques of how to enhance these features when desigining a system

### Scalability

The scalability of a system is all about how it can handle load growth. In plain words a scalable system can handle increasing load without problems. On the other hand a system
that does not scale it cannot. The are various building blocks that we use in distributed systems in order to enhance the scalability attribute:

- Data partiioning
- Message queues
- Load balancing

In general scalability is mostly about spreading the load the system has to process. 
Specifically, A load balancer is a server that sits in front of your application servers and sends each request to one of them. It is what makes horizontal scaling possible, because clients see one address while many machines do the work. Lesson: Introduction to Load Balancing.

Data partitioning splits one large table across several database servers (sharding), so each server holds and searches a smaller piece. It is the database's way of adding more machines. Lesson: Introduction to Data Partitioning.

A message queue holds work that does not need an answer right now, like sending an email or resizing an image. A spike in traffic then fills the queue instead of overloading the servers. Lesson

We start with a setup where everything is hosted on one server, and throughout these notes we discuss the challenges
we need to address, and the techniques we can use to address them, in order to scale the system to millions of users.

Let's consider the case of a web application, following the example in [3]. Initially, we assume that the web application, the database, and the cache all run on the same machine.
There are two types of clients that our web server has to serve: a mobile application and a web application running in the browser. These two clients typically have different requirements in terms of responses (e.g. HTML for the browser, JSON for the mobile app), and our web server needs to account for this.

<!-- TODO: add a figure of the single-server setup with web and mobile clients. -->

Let's look, at a very high level, at the flow of a request coming from a client:

1. A client accesses a website through its domain name, e.g. _mydomain.com_. The browser asks the Domain Name System (DNS) for the IP address of that name; see [Part 6 | Domain Name System](2025-04-18-part-6-domain-name-system.md).
2. DNS returns the IP address to the browser (see the appendix below for how to find the IP address of your machine).
3. The browser sends HTTP requests to the web server at that IP address.
4. The web server returns HTML, JSON, XML, or whatever response it is configured to send.

::: {.callout-note title="Terminology"}
In these notes, a process that runs a service is referred to as a server. A process that sends a request
to a server is referred to as a client.
:::

In the example above, the traffic to our web server comes from the web application and the mobile application. As the number of users grows, hosting everything on a single server becomes infeasible.
We can move the web application and the database to different servers, ending up with a configuration that has a web tier and a database tier.

::: {.callout-note title="Remark"}
One of the advantages of breaking a system apart is that it allows us to scale its parts independently.
However, this does not come for free, and coordination between the parts is one of the problems we will need to solve.
:::

Introducing a separate database tier allows us to scale the data layer independently. However, the web application now has to communicate with the database over the network.
The network is notoriously unreliable, which means that we need to make sure that our system tolerates its failures.

## Summary

::: {.callout-note title="Summary"}
A distributed system is a collection of independent components that run concurrently and communicate over a network to work together as one system, a concept famously illustrated by Leslie Lamport's quip that the failure of a computer you didn't know existed can make your own unusable. These notes use a web application as a running example: initially, a single server may host the web app, database, and cache, while clients (browsers or mobile apps) send requests after resolving a domain name through the Domain Name System. As demand grows, this architecture must evolve by separating components into tiers, such as a web tier and a database tier, so that they can scale independently. Distributing components across machines, however, introduces new challenges, especially coordination and unreliable network communication, which distributed system design must address.
:::

## Appendix: finding your IP address on Linux {.appendix}

There are various ways to find the IP address of a Linux machine, depending on whether you want your local (private) IP address or your public one.

### Local IP address

```bash
ip addr
```

or, shorter:

```bash
ip a
```

Look for `inet` under your active interface (e.g. `eth0`, `ens33`, `wlan0`), for example:

```
inet 192.168.1.25/24
```

For a cleaner output use:

```bash
hostname -I
```

On older systems you can also use `ifconfig` (from the deprecated `net-tools` package).

### Public IP address

The public IP address is the address of your router as seen from the internet. You can ask an external service for it (this requires an internet connection):

```bash
curl ifconfig.me
```

or:

```bash
curl icanhazip.com
```
