# Lesson 11: HTTP

## Overview

In this lesson we discuss the HTTP protocol. It is the main protocol that modern web applications
use for communication, and most REST APIs rely on it.

HTTP is, in general, a simple protocol, but it is the backbone of the web and of modern system architecture.
From basic website browsing to complex microservice interactions, HTTP enables consistent communication between front-end and back-end components.

The first part of the lesson covers HTTP's semantics: requests, methods, responses, and status codes. These are the same in every version of the protocol.
The second part covers how the protocol has evolved, from HTTP/1.1 to HTTP/2 and HTTP/3, to make the web faster. The versions differ in how messages are carried over the network, and they build on the transport protocols discussed in [Lesson 6: TCP](2026-03-17-part-4-TCP_101.md) and [Lesson 8: UDP & QUIC](2026-07-31-TCP-UDP-QUIC.md).

## HTTP semantics

HTTP (HyperText Transfer Protocol) is the foundation of data communication on the web. It defines how clients (like browsers) and servers communicate.
HTTP is a request-response protocol: the client initiates the communication by
sending a request, and the server processes the request and returns a response. Before sending any request, the
client has to connect to the server, usually over [TCP](2026-03-17-part-4-TCP_101.md) (HTTP/3 uses QUIC instead).

### Requests and methods

An HTTP request typically includes:

- A method (what you want to do)
- A URL (the location of the resource)
- Headers (metadata, e.g. the content type)
- A body (optional data)

HTTP defines a number of methods. The most commonly used ones are:

- `GET`: read an existing resource.
- `POST`: create a new resource (or, more generally, submit data to be processed).
- `PUT`: replace a resource with the representation in the request; by convention it contains the full, updated resource. `PUT` can also create a resource at a URL chosen by the client.
- `PATCH`: partially update an existing resource; the request contains only the modifications.
- `DELETE`: delete an existing resource.

`GET` is _safe_ (it does not change server state), and `GET`, `PUT`, and `DELETE` are _idempotent_ (sending the same request several times has the same effect as sending it once). `POST` and `PATCH` are not idempotent in general. This matters when clients retry requests; see [Lesson 39: Replay Attack vs Idempotency Issues](2026-07-30-Replay-Attack-Idempotency.md).

### Responses and status codes

The HTTP server's response includes:

- A status code
- Headers
- A body (the actual content)

The status code tells the client the outcome of the request. The most common status codes and their meanings are:

- `200 OK`: the request succeeded.
- `201 Created`: the request succeeded and a new resource was created.
- `202 Accepted`: the request was accepted and is being processed. This is used for actions that take a long time to complete.
- `301 Moved Permanently`: the resource has moved permanently; the new URL is given in the `Location` header.
- `400 Bad Request`: the request is malformed and should be changed before being sent again.
- `401 Unauthorized`: the request lacks valid authentication credentials (the client is not authenticated).
- `403 Forbidden`: the client is authenticated but does not have permission to access the resource. In UNIX terminology, the current user does not have the privileges to perform the action.
- `404 Not Found`: the resource was not found.
- `405 Method Not Allowed`: the method is not supported by the resource.
- `429 Too Many Requests`: the client has been rate limited.
- `500 Internal Server Error`: the server failed while processing the request.
- `503 Service Unavailable`: the server is temporarily unable to handle the request, e.g. because it is overloaded.

See [Lesson 37: Authentication & Authorization for APIs](2026-10-06-AUTHENTICATION-AUTHORIZATION.md) for more on when to use `401`, `403`, and `404`.

### Key characteristics

- **Stateless:** each request is independent; the server does not remember previous requests.
- **Extensible via headers:** headers enable features like authentication, caching, and content negotiation.
- **Securable with TLS:** HTTP over TLS is HTTPS, i.e. encrypted communication.
- **Independent of the version:** methods, status codes, and headers mean the same thing in HTTP/1.1, HTTP/2, and HTTP/3. Only the way messages are encoded and transported changes.

[API Basics | HTTP Conditional Requests](https://github.com/pockerman/qubit-notes/blob/main/software_engineering/2026-05-05-API-Basics-HTTP-Conditional-Requests.md) discusses conditional HTTP requests. These are requests that use headers (like `If-None-Match` with an ETag, or `If-Modified-Since`) to check whether a resource has changed, so unchanged content isn't downloaded again, reducing server load and saving bandwidth.

::: {.callout-tip title="Further reading"}
The semantics of HTTP are specified in [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110), which obsoletes the older RFC 7231.
:::

## HTTP versions

Over the years, HTTP has evolved to make web pages load faster. A modern web page needs dozens of resources (HTML, CSS, scripts, images), so the main question each version tries to answer is how to fetch many resources at once without one slow or lost response holding up the others.
That problem is called _head-of-line blocking_: the first item in a queue prevents the items behind it from making progress.

### HTTP/1.1: one request at a time

HTTP/1.1 (1997) runs over TCP and introduced persistent connections, so one connection can be reused for several requests. It has inherent limitations for today's web:

- **One request at a time.** Only one request/response can be in flight on a connection; a new request has to wait until the previous response has been fully received. Browsers work around this by opening multiple connections (commonly about six per host), each with its own handshake and slow start.
- **Application-layer head-of-line blocking.** Pipelining lets a client send several requests back to back, but the responses must come back in the same order, so a slow response at the front blocks the rest. Because of this and other problems, browsers never enabled pipelining widely.
- **Verbose, uncompressed headers.** Messages are text-based, and headers, including cookies, are sent in full with every request. For pages that make dozens of requests, this adds significant overhead.

### HTTP/2: multiplexing over one connection

HTTP/2 (2015) fixes HTTP/1.1's inefficiencies while keeping its semantics, so existing applications didn't need to change. Its key features are:

- **Binary framing.** Each HTTP message is split into small binary frames, each tagged with a stream identifier.
- **Multiplexing.** Because frames are tagged, many requests and responses can be in flight at once over a single TCP connection. The server interleaves frames of different responses, and the client reassembles them by stream ID. A slow response no longer holds up faster ones, which removes HTTP/1.1's application-layer head-of-line blocking. Using one connection per origin also means fewer handshakes and less memory and CPU for managing sockets.
- **Header compression (HPACK).** Headers are compressed, and headers sent previously on the connection are not sent again. This cuts bandwidth, especially for many small requests.
- **Stream prioritization.** The client can indicate which streams matter most, e.g. the HTML document or the CSS. The original scheme was complex and inconsistently implemented, and has since been replaced by a simpler one ([RFC 9218](https://www.rfc-editor.org/rfc/rfc9218)).
- **Server push.** A server could send resources before the client asked for them. In practice it often sent data the browser already had cached; Chrome removed support for it in 2022 [5], and it is now considered deprecated.

One problem remains. HTTP/2 still runs over TCP, which delivers bytes strictly in order (see [Lesson 6: TCP](2026-03-17-part-4-TCP_101.md#the-cost-of-tcp)). If a packet carrying part of one stream is lost, TCP holds back the data of _all_ streams on the connection until it is retransmitted. This is transport-layer head-of-line blocking. On reliable networks it is rarely noticeable, but on lossy links (mobile data, congested Wi-Fi) it can cancel out much of the benefit of multiplexing.

### HTTP/3: HTTP over QUIC

HTTP/3 (2022) keeps HTTP/2's model but replaces TCP with QUIC, which runs over UDP (see [Lesson 8: UDP & QUIC](2026-07-31-TCP-UDP-QUIC.md)). Think of it as "HTTP/2 over QUIC":

- **No head-of-line blocking between streams.** QUIC provides independent streams at the transport layer, and HTTP/3 maps each request/response to its own stream. A lost packet only delays its own stream; for example, a dropped packet of an image download does not stall the HTML and CSS.
- **Faster connection setup.** QUIC combines the transport and TLS 1.3 handshakes, so a new connection takes one round trip instead of two for TCP plus TLS 1.3, and a resumed connection can send data immediately (0-RTT).
- **Connection migration.** A connection survives a change of network, e.g. from Wi-Fi to cellular, without a new handshake.
- **Same semantics.** Headers are compressed with QPACK, a variant of HPACK adapted to streams that arrive out of order. Everything else from the first part of this lesson stays the same.

HTTP/3 performs best where HTTP/2 struggles: on mobile networks and long-distance connections with packet loss and high latency. Many CDNs and large websites have enabled it for these reasons.
It does need support from both client and server, and some networks and firewalls block UDP. Browsers therefore discover HTTP/3 support from the server (e.g. via the `Alt-Svc` header) and fall back to HTTP/2 over TCP when QUIC is unavailable.

### Comparing the versions

| Aspect | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| Transport | TCP | TCP | QUIC (over UDP) |
| Message format | Text | Binary frames | Binary frames |
| Concurrent requests per connection | One | Many (multiplexed streams) | Many (independent QUIC streams) |
| Head-of-line blocking | At the HTTP layer | At the TCP layer | None between streams |
| Header compression | None | HPACK | QPACK |
| Encryption | Optional (HTTPS) | Optional in the spec, required by browsers | Always (TLS 1.3) |
| Connection setup with TLS 1.3 | 2 RTT | 2 RTT | 1 RTT (0-RTT on resumption) |

In essence, HTTP has evolved from one request at a time per connection (HTTP/1.1), to multiplexed streams over TCP (HTTP/2), to multiplexed streams over QUIC (HTTP/3).

## Summary

::: {.callout-note title="Summary"}
HTTP is the core protocol of the web. Clients and servers interact through a request–response model. A client sends a request containing a method (e.g., `GET`, `POST`, `PUT`), a URL, headers, and optionally a body, and the server responds with a status code, headers, and content. HTTP defines standard methods for creating, reading, updating, and deleting resources, some of which are safe or idempotent, along with status codes that indicate the outcome of a request (such as `200` for success or `404` for not found). HTTP is stateless, extensible via headers, and securable through TLS (HTTPS), and these semantics are the same in every version. HTTP/1.1 handles one request at a time per connection, so browsers open several connections and slow responses block the ones behind them. HTTP/2 adds binary framing, multiplexing of many streams over one TCP connection, and header compression, but a lost TCP packet still stalls every stream. HTTP/3 runs over QUIC, which gives each stream independent delivery, a faster encrypted handshake, and connection migration, and falls back to HTTP/2 when UDP is blocked.
:::
