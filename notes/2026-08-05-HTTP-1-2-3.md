# Lesson 12: HTTP/1.1, HTTP/2 & HTTP/3

## Overview

HTTP/1.1, HTTP/2, and HTTP/3 are successive versions of the web's [HTTP](2026-04-09-Part-8-HTTP.md) protocol. HTTP/2 introduced multiplexing, i.e. sending multiple requests in parallel over one connection, to overcome HTTP/1.1's head-of-line blocking, where one slow request stalls the others. HTTP/3 builds on this by using QUIC, a UDP-based transport, to also eliminate head-of-line blocking at the transport level, for faster and more reliable web communication.

## Evolution of HTTP

Over the years, HTTP has evolved to make web pages load faster and more efficiently.
Here is a quick overview of how each version improved on its predecessor:

- **HTTP/1.1 (1997).** The long-standing version of HTTP, running over TCP. Only one request/response can be in flight on a connection at a time, so requests are processed sequentially. Browsers therefore open multiple TCP connections (commonly about six per host) to fetch resources in parallel. HTTP/1.1 introduced persistent connections and pipelining, but pipelining suffers from head-of-line blocking: a slow response blocks the ones behind it. Messages are text-based with verbose, uncompressed headers, which adds overhead.
- **HTTP/2 (2015).** A major upgrade focused on performance. HTTP/2 introduced multiplexing: multiple requests and responses can be in flight concurrently over a single TCP connection. It switched to a binary framing layer and added header compression (HPACK), server push, and stream prioritization. Multiplexing removes HTTP/1.1's application-layer head-of-line blocking, but because HTTP/2 still runs over TCP, a lost packet causes head-of-line blocking at the TCP level.
- **HTTP/3 (2022).** The latest version changes the transport: HTTP/3 runs over [QUIC](2026-07-31-TCP-UDP-QUIC.md), which is built on UDP. QUIC provides independent streams at the transport layer, so a lost packet only affects its own stream, eliminating the remaining head-of-line blocking problem of HTTP/2. QUIC also has faster handshakes and mandatory built-in encryption (TLS 1.3).

In essence, HTTP has evolved from one request at a time per connection (HTTP/1.1), to multiplexed streams over TCP (HTTP/2), to multiplexed streams over QUIC (HTTP/3).
Let's now look at head-of-line blocking and multiplexing, which are central to these improvements.

## Head-of-line blocking

Head-of-line (HoL) blocking is a situation where the first item in a queue prevents the items behind it from making progress.
In networking, if one request or packet is delayed, everything behind it waits, even if it could otherwise be processed immediately.

- **In HTTP/1.1 (application-layer HoL blocking).** A connection handles one request at a time, and with pipelining, responses must come back in the same order as the requests. If an early request is slow (e.g. waiting on a slow database query or a large file), it blocks the responses to all later requests on that connection. It's like a single checkout line at a store: if the customer at the front has a problem, everyone behind them waits. Browsers mitigate this by opening several parallel connections, but each connection still processes one request at a time.
- **In TCP (transport-layer HoL blocking).** Even with HTTP/2's multiplexing, the underlying TCP connection can cause head-of-line blocking. TCP delivers bytes strictly in order: if packet #2 is lost, TCP holds back all subsequent data until packet #2 is retransmitted. With HTTP/2, a lost packet carrying part of one stream therefore stalls all the streams on the connection until it is recovered, even though the streams are independent at the HTTP level.

Head-of-line blocking leads to higher latency and inefficient use of the network. With HTTP/1.1, pages with many resources (images, scripts, CSS) loaded slower because the resources could not all be fetched at once.
With HTTP/2, HoL blocking is gone at the HTTP layer, but on lossy networks (e.g. mobile) a single packet loss can still degrade performance because of TCP's in-order delivery.
This is exactly what HTTP/3 tackles by switching the transport to QUIC.

## Multiplexing

Multiplexing is the ability to send multiple data streams over a single channel at the same time.
In HTTP, multiplexing means multiple requests and responses are transmitted in parallel over one connection, instead of one after the other.

With HTTP/1.1, if a web page needs 10 resources, the browser must either use multiple connections or send the requests sequentially, fetching one resource at a time per connection.
This is like mailing the chapters of a book one at a time, waiting for each to be received before sending the next.

HTTP/2's multiplexing changed that. Its binary framing layer breaks each HTTP message into small frames, each tagged with a stream identifier.
A browser can therefore send many requests at once over the same TCP connection and receive the responses as they become ready, in any order.
The server interleaves frames of different responses on the wire, and the client reassembles them by stream ID. In our book analogy, HTTP/2 sends all the chapters in parallel, each in its own numbered envelope, so the recipient can put them in order;
if one chapter is delayed, the others can still be read.

Key points about HTTP/2 multiplexing:

- **Multiple parallel streams.** One TCP connection handles many requests simultaneously. For example, a browser can request all 10 images of a page at once and receive data for all of them interleaved on the same connection.
- **No ordering constraint at the HTTP layer.** Responses are sent as soon as they are ready; a slow response no longer holds up faster ones.
- **Efficiency.** Fewer TCP connections mean less overhead (fewer handshakes, less memory and CPU for managing sockets). Multiplexing also enables prioritization, so that important resources (like the HTML or CSS) can be delivered first.

HTTP/3 keeps the multiplexing model but implements the streams in the transport layer, via QUIC.
Since each QUIC stream is independent, a packet lost on one stream does not block the others, something HTTP/2 over TCP cannot achieve.
This makes web transfers more robust, especially on unreliable networks.

## The versions in more detail

### HTTP/1.1: sequential requests

HTTP/1.1 was a big step forward in the late 1990s, introducing persistent connections and pipelining, but it has inherent performance limitations for today's web:

- **One request at a time.** Each connection handles one request at a time; a new request has to wait until the previous response has been fully received. Browsers work around this by opening multiple connections (typically six per host), but each connection still processes its requests sequentially.
- **Head-of-line blocking.** Pipelining lets a client send several requests back to back, but the responses must still come back in order, so a slow response at the front blocks the rest. Because of this and other problems, pipelining was never widely enabled by browsers.
- **Verbose, uncompressed headers.** HTTP/1.1 sends text headers, including cookies, with every request, and has no header compression. For modern websites that make dozens of requests, this adds significant overhead.

### HTTP/2: multiplexing and performance improvements

HTTP/2 was designed to fix HTTP/1.1's inefficiencies while keeping its semantics (methods, status codes, headers), so existing applications didn't need to change.
Its key features are:

- **Multiplexed streams over one connection.** As discussed, multiple requests and responses can share a single TCP connection without waiting for each other. This greatly improves load times for resource-heavy pages.
- **Binary framing.** HTTP/2 replaces HTTP/1.1's text format with a compact binary format. This makes parsing more efficient and less ambiguous, and frames from different streams can be interleaved.
- **Header compression (HPACK).** Instead of repeatedly sending large headers (like cookies and user agents), HTTP/2 compresses them and remembers previously sent headers. This cuts bandwidth, especially for many small requests.
- **Server push.** A server can proactively push resources to the client, e.g. the CSS and JavaScript files of a page before the browser asks for them. In practice, push often sent data the browser already had cached, and it was hard to use well; Chrome removed support for it in 2022, and it is now considered deprecated.
- **Stream prioritization.** The client can indicate which streams matter most, e.g. the HTML document or above-the-fold images. HTTP/2's original prioritization scheme was complex and inconsistently implemented, and has since been replaced by a simpler scheme ([RFC 9218](https://www.rfc-editor.org/rfc/rfc9218)).

The result is faster and smoother loading of websites with many assets, using a single connection per origin and therefore less memory and CPU for managing sockets.
News sites and social media platforms that serve many images and scripts benefit greatly from HTTP/2's multiplexing and header compression.

However, one caveat remains: because HTTP/2 runs over TCP, when the network drops a packet, all the streams on the connection pause until the packet is retransmitted.
On reliable, low-latency networks this is rarely noticeable, but on lossy links (mobile data, congested Wi-Fi), it can negate some of the benefits of multiplexing. Enter HTTP/3.

### HTTP/3: QUIC and the end of head-of-line blocking

HTTP/3 is essentially HTTP/2's model adapted to run on QUIC, a transport protocol that runs over UDP.
QUIC was developed at Google and standardized by the IETF to solve the transport-layer problems that HTTP/2 could not solve on top of TCP.
Here is what changed:

- **QUIC instead of TCP.** QUIC provides reliability, ordering, and encryption at the transport layer, but it does not enforce in-order delivery across the whole connection. Instead, a QUIC connection carries multiple independent streams: if a packet in one stream is lost, only that stream waits for the retransmission, while the others continue. HTTP/3 maps each request/response to a QUIC stream and inherits this behaviour. For example, a dropped packet belonging to an image download won't stall the HTML and CSS streams.
- **Built-in encryption and faster handshakes.** QUIC always uses TLS 1.3 and combines the transport and cryptographic handshakes into one. A fresh connection is established in one round trip (1-RTT), compared to two for TCP plus TLS 1.3 and three for TCP plus TLS 1.2; a resumed connection can send data immediately (0-RTT). This is especially beneficial for mobile clients and real-time applications.
- **Other QUIC benefits.** QUIC supports connection migration: when a device switches from Wi-Fi to cellular, the connection continues, identified by its connection ID, without a new handshake. QUIC's congestion control and loss recovery also run in user space and can evolve faster than TCP's.
- **Same HTTP semantics.** HTTP/3 doesn't change HTTP's semantics. It still has streams, header compression (QPACK, a variant of HPACK adapted to out-of-order delivery), and so on. The big change is the transport. Think of HTTP/3 as "HTTP/2 over QUIC".

### Why HTTP/3 matters

By removing the last source of head-of-line blocking, HTTP/3 can outperform HTTP/2 under adverse network conditions, such as packet loss and high latency.
Users on mobile networks or long-distance connections often see more consistent performance with HTTP/3, with fewer stalls due to lost packets.
Moreover, the faster handshake means that every HTTPS connection starts up faster.
Many CDNs and large websites have enabled HTTP/3 for these reasons.

That said, HTTP/3 requires support from both the client and the server, and some networks and corporate firewalls block UDP traffic.
Browsers therefore discover HTTP/3 support (e.g. via the `Alt-Svc` header) and fall back to HTTP/2 over TCP when QUIC is unavailable.
HTTP/3 support is now widespread in browsers, servers, and CDNs, and its adoption keeps growing.

## Summary

::: {.callout-note title="Summary"}
HTTP/1.1 processes one request at a time per connection, so browsers open several connections, and slow responses cause application-level head-of-line blocking; its text headers are verbose and uncompressed. HTTP/2 keeps HTTP's semantics but adds binary framing, multiplexing of many streams over a single TCP connection, HPACK header compression, and prioritization (server push turned out to be a failure and is deprecated). Because HTTP/2 still runs over TCP, a single lost packet stalls all streams: transport-level head-of-line blocking. HTTP/3 runs over QUIC, which provides independent, encrypted streams over UDP, eliminating head-of-line blocking between streams, establishing connections in 1-RTT (0-RTT on resumption), and supporting connection migration. HTTP/3 shines on lossy and mobile networks, but needs UDP to be allowed and falls back to HTTP/2 when it isn't.
:::
