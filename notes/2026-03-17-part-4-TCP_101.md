# Lesson 6: TCP

## Overview

[Lesson 5: Inter-Process Communication](2026-03-16-part-3-OSI_MODEL.md) discussed how two remote processes communicate
with each other through a layered communication architecture, with the application layer at the top.
In this architecture, each layer depends on the abstractions exposed by the layer below it.
Below the application layer is the transport layer, which usually employs the [Transmission Control Protocol](https://en.wikipedia.org/wiki/Transmission_Control_Protocol) (TCP) to transmit data between two processes. In this lesson we discuss how TCP works, what it costs, and when to use it. You can find an overview of TCP here: [Transmission Control Protocol](https://www.sciencedirect.com/topics/computer-science/transmission-control-protocol).
The alternatives to TCP, UDP and QUIC, are discussed in [Lesson 8: UDP & QUIC](2026-07-31-TCP-UDP-QUIC.md).

## Reliable delivery

TCP is a connection-oriented transport-layer protocol. It operates on top of IP
and guarantees that a stream of bytes arrives in order, without gaps, duplication, or corruption [1]. TCP also implements flow control and congestion control
algorithms to avoid overwhelming the receiver or the network.

The most important trait of TCP is its reliability. TCP achieves reliability by partitioning a byte stream into discrete packets
called segments [1]. Segments are sequentially numbered, which allows the receiver to detect
gaps and duplicates, and to put segments that arrive out of order back in order. Every segment sent has to be acknowledged by the receiver. If the sender does not receive an acknowledgment for a segment
within a certain time, it retransmits the segment [1]. Each segment also carries a checksum that the receiver uses to verify the integrity of the data.

## Connection lifecycle

A TCP connection goes through many states, but the most important ones are:

- Opening
- Established
- Closing

A connection is identified by a 4-tuple: the source IP address and port, and the destination IP address and port. If any of them changes, for example when a phone switches from Wi-Fi to cellular data, the connection breaks and a new one has to be opened.

During the opening state a connection is being created. A server must be listening for connection requests from clients before a connection can be established.
TCP uses a three-way handshake to create a new connection [1]:

1. The sender picks a random sequence number $x$ and sends a SYN segment to the receiver.
2. The receiver increments $x$, chooses its own random sequence number $y$, and sends back a SYN/ACK segment.
3. The sender increments both sequence numbers and replies with an ACK segment, which can carry the first bytes of application data.

Only after this handshake do the two sides exchange data, which ensures both are ready and have agreed on sequence numbers.
The handshake costs a full round trip during which no application data is sent; the connection's bandwidth is effectively zero until it has been opened.
The lower the round-trip time, the faster a connection is established. This is why we want servers close to their clients, and why we reuse
connections that are already open. If the connection is secured with TLS, the TLS handshake adds at least one more round trip on top (see [Lesson 7: TLS 101](2026-04-06-Part-5-TLS-101.md)).

Once the transmission is complete, the connection has to be closed and its resources released by both sides; otherwise resources leak.
Closing a TCP connection also involves several round trips [1]: each side sends a FIN segment, which the other side acknowledges. The side that closes first then waits in the `TIME_WAIT` state for a while, so that delayed segments of the old connection are not mistaken for segments of a new one [2].

## Flow and congestion control

**Flow control** prevents the sender from overwhelming the receiver. The receiver stores incoming segments in a receive buffer until the application processes them.
With every ACK, the receiver tells the sender how much free space its buffer has (the receive window), and the sender never sends more unacknowledged data than fits in it.
This approach is not too different from [rate limiting](2026-02-09-Upstream-Resiliency.md) [1].

**Congestion control** guards against overwhelming the underlying network. TCP estimates the available bandwidth of the network and maintains
a _congestion window_: the number of outstanding segments that can be sent without being acknowledged by the receiver [1].
The smaller the congestion window, the fewer bytes are in flight and therefore the less bandwidth is used. When a new connection is established, the congestion window is set to a system default.
During _slow start_, the window grows by one segment for every acknowledged segment, which doubles it every round trip, i.e. it grows exponentially until it reaches a threshold [1]. This is why we cannot use the full bandwidth of the network
as soon as a connection is established. In fact, the bandwidth a TCP connection can achieve is bounded by [1]:

$$
\text{Bandwidth} = \frac{\text{Window size}}{RTT}
$$

When a segment is lost, detected either by a retransmission timeout or by duplicate acknowledgments, TCP considers the network congested and reduces the congestion window. Successful transmissions grow the window again, up to a maximum.

## The cost of TCP

All in all, TCP is a reliable and stable protocol, but its guarantees are not free. It can suffer from higher latency and lower bandwidth than the underlying network is capable of:

- **Connection setup.** The handshake costs a round trip before any data is sent, and TLS adds more.
- **Slow start.** A new connection cannot use the full bandwidth of the network straight away.
- **Head-of-line blocking.** TCP delivers bytes strictly in order. If one segment is lost, everything behind it waits for the retransmission, even if it has already arrived. When several independent streams are multiplexed over one connection (as HTTP/2 does), a single lost packet stalls all of them.
- **Connection identity.** The connection is tied to the 4-tuple, so it does not survive a change of network.
- **Slow to evolve.** TCP is implemented in operating system kernels, and its headers are visible to every router and firewall on the path, so changes to the protocol take years to deploy.

If reliability and ordering are not needed or do not make sense for the application at hand, protocols such as the [User Datagram Protocol (UDP)](https://www.sciencedirect.com/topics/computer-science/user-datagram-protocol) can be used instead. For example, the [Domain Name System](2025-04-18-part-6-domain-name-system.md) uses UDP for most queries, and falls back to TCP for large responses [1]. QUIC, which runs over UDP, removes most of the costs listed above; both are discussed in [Lesson 8: UDP & QUIC](2026-07-31-TCP-UDP-QUIC.md).

## When to use TCP

Use TCP when you need reliable, ordered delivery and cannot tolerate data loss, and when accuracy is more important than speed. TCP is the backbone of most internet applications. Typical use cases:

- **Web pages and file downloads:** every byte must arrive intact, since a missing packet could break a page or corrupt a file.
- **Email and messaging:** protocols like SMTP and IMAP use TCP so that messages arrive complete.
- **Financial transactions and critical data:** banking, payments, and database connections, where data integrity is paramount.
- **General client-server APIs:** TCP (with TLS) is the default for request/response APIs because it handles retransmission and ordering for you.

## Summary

::: {.callout-note title="Summary"}
TCP is a connection-oriented transport-layer protocol that provides reliable communication between processes. It delivers an ordered, complete, and error-free byte stream by splitting data into numbered segments, requiring acknowledgments, retransmitting lost segments, and verifying integrity with checksums. Connections are identified by the source and destination IP addresses and ports, are established with a three-way handshake (SYN, SYN/ACK, ACK), which costs a full round trip before data transfer begins, and are later closed with FIN exchanges. Flow control adapts the sending rate to the receiver's buffer, and congestion control protects the network with a congestion window that grows (exponentially during slow start) with successful transmissions and shrinks when loss is detected. These mechanisms make TCP reliable and stable, but they cost latency and bandwidth, cause head-of-line blocking, and tie a connection to one network path. TCP is the default for web pages, file transfers, APIs, and databases; when its costs matter more than its guarantees, UDP or QUIC may be a better fit.
:::
