# Part 4 | TCP 101

## Overview

[Part 3 | Inter-Process Communication](2026-03-16-part-3-OSI_MODEL.md) discussed how two remote processes communicate
with each other through a layered communication architecture, with the application layer at the top.
In this architecture, each layer depends on the abstractions exposed by the layer below it.
Below the application layer is the transport layer, which usually employs the [Transmission Control Protocol](https://en.wikipedia.org/wiki/Transmission_Control_Protocol) (TCP) to transmit data between two processes. In this note we briefly discuss how TCP works. You can find an overview of TCP here: [Transmission Control Protocol](https://www.sciencedirect.com/topics/computer-science/transmission-control-protocol).

## TCP 101

TCP is a transport-layer protocol. It operates on top of IP
and guarantees that a stream of bytes arrives in order, without gaps, duplication, or corruption [1]. TCP also implements flow control and congestion control
algorithms to avoid overwhelming the receiver or the network.

The most important trait of TCP is its reliability. TCP achieves reliability by partitioning a byte stream into discrete packets
called segments [1]. Segments are sequentially numbered, which allows the receiver to detect
gaps and duplicates, and every segment sent has to be acknowledged by the receiver. If the sender does not receive an acknowledgment for a segment
within a certain time, it retransmits the segment [1]. Each segment also carries a checksum that the receiver uses to verify the integrity of the data.

A TCP connection goes through many states, but the most important ones are:

- Opening
- Established
- Closing

During the opening state a connection is being created. A server must be listening for connection requests from clients before a connection can be established.
TCP uses a three-way handshake to create a new connection [1]:

1. The sender picks a random sequence number $x$ and sends a SYN segment to the receiver.
2. The receiver increments $x$, chooses its own random sequence number $y$, and sends back a SYN/ACK segment.
3. The sender increments both sequence numbers and replies with an ACK segment, which can carry the first bytes of application data.

The handshake costs a full round trip during which no application data is sent; the connection's bandwidth is effectively zero until it has been opened.
The lower the round-trip time, the faster a connection is established. This is why we want servers close to their clients, and why we reuse
connections that are already open. Once the transmission is complete, the connection has to be closed and its resources released by both sides; otherwise resources leak.
Closing a TCP connection also involves several round trips [1].

### Flow and congestion control

**Flow control** prevents the sender from overwhelming the receiver. The receiver stores incoming segments in a receive buffer until the application processes them.
With every ACK, the receiver tells the sender how much free space its buffer has (the receive window), and the sender never sends more unacknowledged data than fits in it.
This approach is not too different from [rate limiting](2026-02-09-Upstream-Resiliency.md) [1].

**Congestion control** guards against overwhelming the underlying network. TCP estimates the available bandwidth of the network and maintains
a _congestion window_: the number of outstanding segments that can be sent without being acknowledged by the receiver [1].
The smaller the congestion window, the fewer bytes are in flight and therefore the less bandwidth is used. When a new connection is established, the congestion window is set to a system default.
During _slow start_, the window grows by one segment for every acknowledged segment, which doubles it every round trip, i.e. it grows exponentially until it reaches a threshold [1]. This is why we cannot use the full bandwidth of the network
as soon as a connection is established. In fact, the bandwidth a TCP connection can achieve is bounded by [1]:

$$
\text{Bandwidth} = \frac{\text{Window size}}{RTT}
$$

When a segment is lost, detected either by a retransmission timeout or by duplicate acknowledgments, TCP considers the network congested and reduces the congestion window. Successful transmissions grow the window again, up to a maximum.

All in all, TCP is a reliable and stable protocol, but it can suffer from higher latency and lower bandwidth than the underlying network is capable of.
If reliability and ordering are not needed or do not make sense for the application at hand, protocols such as the [User Datagram Protocol (UDP)](https://www.sciencedirect.com/topics/computer-science/user-datagram-protocol) can be used instead. For example, the [Domain Name System](2025-04-18-part-6-domain-name-system.md) uses UDP for most queries, and falls back to TCP for large responses [1]. See also [TCP, UDP & QUIC](2026-07-31-TCP-UDP-QUIC.md).

## Summary

::: {.callout-note title="Summary"}
TCP is a transport-layer protocol that provides reliable communication between processes. It delivers an ordered, complete, and error-free byte stream by splitting data into numbered segments, requiring acknowledgments, retransmitting lost segments, and verifying integrity with checksums. Connections are established with a three-way handshake (SYN, SYN/ACK, ACK), which costs a full round trip before data transfer begins, and are later closed through additional exchanges. Flow control adapts the sending rate to the receiver's buffer, and congestion control protects the network with a congestion window that grows (exponentially during slow start) with successful transmissions and shrinks when loss is detected. These mechanisms make TCP reliable and stable, but they limit latency and bandwidth utilization, which is why UDP may be preferred when reliability is less critical.
:::
